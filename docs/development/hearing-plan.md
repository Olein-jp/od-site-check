# 定型ヒアリング統合の実装方針（#18）

基準: d35f829、プラグイン0.3.0、診断Schema 1.2。2026-10-24の「順に着手し、Issueごとにコミット・クローズして次へ進む」という利用者の指示に基づき、以下を採用して継続する。

1. **信頼境界と出力**: `render_result()` が生成する診断だけのJSONを従来同様HMAC署名する。コピー／ダウンロードの明示操作時のみ同一サイトの認証済み `admin-post.php` にPOSTし、新しい準備ハンドラでmanage_options・nonce・署名・list_usersを再検査する。署名済み診断と許可された回答からPHPで統合・整形したJSONと署名を返し、コピーはその文字列、ダウンロードは同じ文字列を既存ハンドラへ送る。旧ハンドラも完成したhearingを必須にして迂回を拒否する。署名は現在の利用者・セッション・サイトに結び付け、秘密はPHP側だけに置く。外部送信、保存、ログ出力は追加しない。
2. **状態と時刻**: 回答はDOM／タブ内メモリのみ。最初の出力要求でサーバーがcompleted_atを確定し、同じスナップショットへの後続出力は署名済み完成JSONを再検証してそのまま返す。毎クリックの再採番はしない。回答変更でキャッシュを破棄し、進行中の古い応答も世代番号で破棄する。既存POST画面に合わせ再診断は回答を保持せず、新しいページから始める。再診断開始・失敗・取消、離脱・再読込・BFCache復帰時に古い結果を出力しない。
3. **単一定義と検証**: `schemas/hearing-1.0.json` に20問のID・文面・区分・選択肢・条件を固定し、PHPとJSが同じ定義を使用する。新しいPHPクラスと小さなJSモデルで13／20問、明示回答、非該当を検証する。準備リクエストはオブジェクトの同名キー消失を避けるため、`[ID,status,answer]` の配列を送る。重複ID・要素数・型・コード・条件不整合を厳密に拒否する。完成JSONはサーバーでのみ生成・署名するため、未署名の任意JSONをそのまま採用しない。
4. **Schemaと版**: トップレベルSchemaを1.3、hearingを1.0とする。完成出力はhearing全20キー必須。Schema内に診断のみの内部snapshot定義を設け、収集テストと署名対象の検証を完成出力と区別する。既存コードに旧22問hearingの実装・出力はなく、同版の混在はない。質問定義変更時はhearing版を分ける。機能追加のため配布準備#23でプラグイン版を0.4.0に統一し、タグ・公開は行わない。
5. **変更と検証**: #19は質問定義／PHP検証／Schema、#20は管理画面／JSモデル／CSS、#21は署名付き準備・出力、#22は統合テスト／ブラウザ確認、#23は文書／サンプル／版管理／ZIP許可リスト。既存22診断項目の収集処理は変更しない。PHPUnit・PHPCS、Node標準テスト、実ブラウザ、PHP 7.4／8.3の既存互換性環境とZIP smokeを使う。読み上げや利用者の受入など代行できない確認は未実施と記録する。既存README・許可リスト・出力仕様の原稿は保全し、既存差分を勝手にコミットしない。

## 現行コードとの対応

- `includes/class-admin.php`: 診断はPOST応答のリクエスト内だけに存在。従来は未回答でもJSONプレビューと署名付きダウンロードが利用できるため、完成出力の検証を追加する。
- `includes/class-exporter.php`: HMACは従来JSON全体のみ。回答をブラウザで追記すると署名が壊れるため、準備ハンドラで統合後に署名し直す。
- `assets/admin.js`: 従来のコピーはtextareaを直接参照する。改変された表示値を正本にせず、検証済み応答を使う。
- `tests/Integration/DiagnosticTest.php`: 収集結果のSchema検証とダウンロード実ハンドラの既存テストがある。前者は内部snapshot定義、後者は完成出力に合わせて維持する。

## 制約の解釈

入力中の自動送信は禁止し、回答変更ではネットワーク処理を行わない。利用者が明示的に出力を要求した時の、同じWordPress内での検証POSTは既存ダウンロード同様の一時処理とする。診断・回答はサーバーにも永続化しない。スクリーンリーダーの実機確認と利用者の受入は、未確認のまま完了としない。
